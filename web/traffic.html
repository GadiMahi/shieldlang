Traffic Lab

Take a recording — a fixed list of HTTP requests, some legitimate and some attacks — and replay it through a real local gateway that applies your ShieldLang policy in front of a small demo backend. You get two independent answers: what the gateway decided, and what the backend actually did. Comparing them is the point: a gateway that says “denied” but whose backend still changed state has failed, and the ledger is what proves it.

  1. Pick a policy and a recording
  2. Pick a mode
  3. Run it
  4. Compare decisions with the ledger
  5. Export the evidence

Everything runs on 127.0.0.1 only. Each run is stored on the server under a stable run id together with the exact versions (fingerprints) of the policy, recording and protocol that produced it.

Plain-English glossary (click to open)
Policy
The ShieldLang rules (and optionally a protocol) the gateway applies to each request.
Recording
A saved, ordered list of requests with their callers. Some entries carry an author-supplied label: legitimate, or illegitimate (an attack).
Enforce
The gateway blocks what the policy forbids. A denied request is never forwarded.
Observe-only
The gateway forwards everything and just records what it would have decided. Those “would” values are predictions: the backend still received the request, so the ledger may show effects enforcement would have prevented.
Decision vs Would
Decision is what actually happened to the request (allow / deny / forwarded / unknown). Would is only filled in for observe-only runs.
Backend ledger
The demo backend's own log of effects. It is the ground truth: it doesn't consult the gateway or the protocol runtime.
Evaluation matrix
Counts only labelled entries. “Blocked” = denied (enforce) or would-be-denied (observe). TP: attack blocked · FN: attack let through · FP: legitimate request blocked · TN: legitimate request allowed.
Latency
Per-request time through the gateway on this machine — useful for comparing modes, not a benchmark.
Run id / fingerprints
Stable identifiers. Re-opening a past run shows exactly the versions it was run against, even if you've since edited the policy.

Only policies whose rules actually match the demo backend's order routes can be usefully replayed here — the Policy dropdown says so for each one.

Import your own recording (JSON)

Paste a recording with the same shape as the bundled ones: {"entries":[{"id","method","path","identity","body","label","fault","save_as"}, …]}. Paths must start with /api/ (the demo backend's only routable prefix); headers besides Content-Type and a fixed set of fault values are not accepted. Check validates without saving and reports every problem with its exact location; Import only succeeds once there are none.
