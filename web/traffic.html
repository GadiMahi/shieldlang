How this page works · glossary

You get two independent answers: the gateway’s decision for each request, and the backend’s own ledger of effects. A gateway that says “denied” while the backend still changed state has failed — and the ledger is what proves it.

Everything runs on 127.0.0.1. Each run is stored under a stable run id with the exact fingerprints of the policy, recording and protocol that produced it.

Policy
The ShieldLang rules (and optionally a protocol) the gateway applies to each request.
Recording
An ordered list of requests with their callers. Entries may carry an author-supplied label: legitimate or attack.
Enforce
The gateway blocks what the policy forbids. A denied request is never forwarded.
Observe-only
Everything is forwarded; the gateway records what it would have decided. The ledger may show effects enforcement would have prevented.
Decision vs Would
Decision is what actually happened. Would is filled in only for observe-only runs.
Backend ledger
The demo backend’s own log of effects — ground truth that never consults the gateway.
Evaluation matrix
Labelled entries only. TP attack blocked · FN attack let through · FP legitimate request blocked · TN legitimate request allowed.
Latency
Per-request time through the gateway on this machine — for comparing modes, not a benchmark.
