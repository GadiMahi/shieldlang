Bypass Lab

A filter and the application behind it can read the same text differently — for example, the app decodes %2e or full-width characters that the filter never saw. Search for inputs that slip past the filter, see both readings side by side, and shrink each finding to its essence.

How this page works · glossary

If the filter checks one interpretation (say, the raw text) and the application acts on another (say, after decoding percent-escapes), an input can look harmless to the filter and harmful to the application. Each scenario (“fixture”) declares both pipelines and what counts as a violation.

Fixture
One named scenario: where the input goes, how the policy reads it, how the application reads it, and what counts as a violation.
Pipeline
The ordered steps a side applies before using the text — e.g. percent_decode, nfkc, strip_nul.
Policy view / App view
What the filter ends up checking, and what the application ends up using.
Oracle
An independent definition of “violation” (e.g. “contains <script”), evaluated on the app’s view.
Local replay
The input is actually sent (loopback only) to a tiny local fixture app to confirm the behaviour.
Confirmed
All three at once: the policy accepts it, the oracle flags the app’s view, and the replay confirms it.
Negative control
A fixture where both sides read input identically — it shows the lab doesn’t cry wolf.

Scope. What is searched: only the selected fixture's declared transformations and local application. Seeds come from its oracle, not the preset bypass examples. A finding needs policy acceptance, an oracle violation and local replay; no finding within a budget is not proof of safety. These experiments never scan external websites or arbitrary .shl policies.
