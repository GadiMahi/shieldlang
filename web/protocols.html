Protocol Studio rules about the ORDER of requests

Protocol Studio

A normal ShieldLang rule judges one request at a time ("is this field well-formed?"). A protocol judges the order of requests: an order may only be paid after it is created, only be confirmed after it is paid, and the card used to confirm must be the same card used to pay. This page lets you write such a protocol, check it, and then fire real requests at it to watch what the runtime does — including when the network lies about whether a payment went through.

Nothing on this page is simulated in the browser. Your source is compiled by the real ShieldLang compiler, requests pass through a real local gateway (loopback only) to a small demo backend, and every table on the right is read back from the server after each action.

Plain-English glossary (click to open)
Protocol
A small state machine for one kind of thing (here an order): its states, and which request rule is allowed to move it from one state to the next.
Resource
One live instance of that thing — e.g. order ord_1, currently in state paid, owned by alice.
Reservation
Before a request is forwarded, the runtime reserves the resource atomically so two requests can't move it at once. The reservation is written to disk before the backend is called, so a crash can't make it disappear.
Committed / Released
Committed: the backend definitely applied the change, so the resource moves to its new state. Released: the backend definitely did not apply it, so the resource stays where it was.
Unknown
We sent the request but can't tell whether it took effect (timeout, dropped response, unexpected status). The resource is frozen — further requests on it are refused — until evidence settles it. It is never guessed.
Reconcile
Settling an Unknown with evidence: the runtime asks the backend what the resource looks like now (a "probe"), or an operator supplies written evidence. There is deliberately no "mark as success" button.
Enforce vs Observe-only
Enforce: the gateway blocks requests the protocol forbids. Observe-only: everything is forwarded; the gateway just records what it would have blocked. Observe results are predictions, never outcomes.
Backend ledger
The demo backend's own record of what it actually did. It is independent of the protocol runtime, so it is the ground truth against which the runtime's beliefs can be compared.
Hash
A fingerprint of the exact protocol (sha256:…). If you edit the source, the hash changes, and evidence from an older session is flagged as stale.

1 Write and check the protocol

What this is. ShieldLang source: rule blocks describe what a single request must look like; the protocol block describes the allowed order. Pick an example or edit the text, then press Check protocol. Checks run on the compiler, not on live traffic.

2 What the protocol allows

How to read it. Each pill is a state. A request rule may move a resource along an arrow, and no other way. Anything that isn't an arrow (e.g. confirming an order that was never paid) will be refused by the runtime.
Honest scope: this graph only shows that states are connected. It is not a proof that every order can always finish.

Press “Check protocol” to see the states and the moves between them.

3 Start a session

What a session is. A private run of this protocol: its own database file, its own demo backend, its own gateway (all on 127.0.0.1). Starting one gives you somewhere safe to send requests and break things. Closing it throws it away.

No active session yet. Check the protocol first (step 1), then start one.

Try a scenario — each button fills in the form below and tells you what to expect. Run them in order the first time. “Use the last order” means the order id returned by your most recent create.

5 Recover and reconcile

Locked until a session is running (step 3).

When a request ended as unknown: the order is frozen. Type its id (filled in for you after a create) and press Reconcile by probe — the runtime asks the backend what the order looks like now, but only trusts the answer after a short quiet period (so a slow request that is still in flight can't fool it). If the probe is inconclusive you can resolve it by hand with written evidence.
Restart session simulates a process restart: the runtime reopens the same database and runs its recovery pass (a reservation with no send record is released; one that was sent but has no recorded outcome becomes Unknown — never silently released).
