How this page works · glossary

A normal ShieldLang rule judges one request at a time (“is this field well-formed?”). A protocol judges the sequence: which request may move an order from one state to the next, who owns it, and which values must match between steps.

Nothing here is simulated in the browser. Your source is compiled by the real ShieldLang compiler, requests pass through a real local gateway (loopback only) to a small demo backend, and every table is read back from the server after each action.

Protocol
A small state machine for one kind of thing (here an order): its states, and which request rule may move it to the next state.
Resource
One live instance, e.g. order ord_1, currently paid, owned by alice.
Reservation
Before forwarding, the runtime reserves the resource atomically so two requests can’t move it at once. It is written to disk before the backend is called.
Committed / Released
Committed: the backend definitely applied the change. Released: it definitely did not.
Unknown
The request was sent but the outcome is unclear (timeout, lost response). The order is frozen until evidence settles it — never guessed.
Reconcile
Settling an Unknown with evidence: a probe of the backend, or written operator evidence. There is no “mark as success” button.
Enforce / Observe-only
Enforce blocks what the protocol forbids. Observe-only forwards everything and records what it would have blocked.
Backend ledger
The demo backend’s own record of what it did — independent ground truth for checking the runtime.
Hash
A fingerprint of the exact protocol (sha256:…). Editing the source changes it, and older evidence is flagged as stale.

Steps

1 Write and check the protocol

rule blocks describe a single request; the protocol block describes the allowed order. Pick an example or edit the source, then press Check protocol.

2 What the protocol allows

Each pill is a state; a request may only move an order along an arrow. Anything else — like confirming an unpaid order — is refused.

Check the protocol to see its states and the moves between them.

This graph shows which states are connected. It is not a proof that every order can always finish.

3 Start a session

A session is a private sandbox: its own database, demo backend and gateway, all on 127.0.0.1. Closing it throws it away.

No active session yet. Check the protocol first, then start one.

4 Send requests

Available once a session is running.

Try a scenario. Each button fills in the form and tells you what to expect — run them in order the first time.

5 Recover and reconcile

Available once a session is running.

If a request ends as unknown, the order is frozen. Reconcile by probe asks the backend what really happened (after a short quiet period). Restart session simulates a crash and runs the recovery pass — nothing is ever silently released.
